# 📋 0050 + 00631L 投資組合動態槓桿計算器 — 產品需求規劃文件 (PRD)

本文件（Product Requirement Document, PRD）旨在明確定義「0050 與 00631L 投資組合動態槓桿計算器」的功能需求、非功能需求、使用者情境（User Stories）以及未來的產品藍圖。本文件將作為後續工程開發、功能測試與介面對接（如 LINE/WhatsApp Bot）的依據。

> **技術實作：** 後端採用 **Node.js + Express + TypeScript** 開發。詳細架構、目錄結構、API 契約與開發流程請參閱 [Express + TypeScript 技術開發文件](./technical-spec-express-typescript.md)。

## 1. 產品宗旨與痛點解決 (Product Purpose)

### 1.1 背景
在台股指數化投資領域，許多投資者採用「元大台灣50 (0050)」搭配「元大台灣50正2 (00631L)」來進行資產配置。這種配置可以利用正2的 2 倍槓桿效應放大曝險、釋出更多現金，或是調整組合以達到個人理想的整體實質槓桿倍數（例如 1.2 倍、1.5 倍）。

### 1.2 核心痛點
* **動態槓桿漂移盲點：** 股票市場每日漲跌，00631L 的波動通常是 0050 的兩倍。隨著時間推移，兩者的**市值比例會隨市場劇烈改變**，導致初始設定的槓桿倍數「漂移」，投資人可能在不知不覺中暴露於過高或過低的風險中。
* **手動查價計算繁瑣：** 投資人若要得知當前的「實質整體槓桿倍數」，每次都必須手動開啟看盤軟體查閱兩檔標的的今日收盤價，並手動代入複雜公式（總曝險金額 / 總淨值），極耗時間且容易忙中算錯。
* **缺乏組合風控檢視：** 目前市面上的看盤軟體僅提供個別資產的損益，不提供「跨資產組合後的加權實質槓桿率」。

### 1.3 產品定位
一個輕量、精準、具備自動化財經 API 串接能力的財務計算核心。使用者只需輸入庫存，系統能自動抓取市場最新股價，並一鍵回傳投資組合的即時現況、損益狀態與當前實質動態槓桿。

## 3. 功能需求明細 (Functional Requirements)

### 3.1 核心計算引擎需求 (FR-01)
* **FR-01-1 成本與庫存記錄：** 系統必須支援輸入 0050、00631L 的每股成本（浮點數）與持有股數（正整數）。
* **FR-01-2 總淨值計算：** 系統必須計算當前總市值（$0050當前現價 \times 0050股數 + 00631L當前現價 \times 00631L股數$）。
* **FR-01-3 實質曝險計算：** 系統必須依據槓桿定義計算總曝險（$0050現貨市值 \times 1 + 00631L正二市值 \times 2$）。
* **FR-01-4 整體槓桿倍數：** 系統必須輸出精確到小數點後三位的整體槓桿值（總曝險 / 總淨值）。

### 3.2 外部股票 API 自動串接功能需求 (FR-02)
* **FR-02-1 開放財經數據庫對接：** 後端程式必須整合 HTTP 請求模組（如 `axios`），自動串接第三方財經資料源（如免認證的 FinMind API），精準識別 `0050` 與 `00631L` 兩個台股標的。
* **FR-02-2 時間序列防禦機制：** 考量到使用者可能在週末、例假日或非開盤時段執行程式，API 請求模組必須具備時間範圍覆蓋能力（例如自動拉取過去 7 天內之數據），並過濾出**最新一個交易日**的收盤價，確保系統不因當日無開盤而中斷。
* **FR-02-3 異常容錯機制 (Fallback Prices)：** 當第三方 API 伺服器發生不可抗力之斷線、網址失效、回應逾時或回傳空值時，系統必須能自動載入寫死於配置檔中的預設防禦股價（例如 0050 使用 160.0、00631L 使用 210.0）完成基礎財務計算，且必須在控制台/日誌中明確拋出錯誤警告。

### 3.3 使用者介面與輸出需求 (FR-03)
* **FR-03-1 CLI 互動終端（階段一）：** 提供友善的提示引導使用者依序輸入資料，並在自動串接完最新股價後，以結構化、排版美觀的格式印出報表。
* **FR-03-2 行情與損益格式化：** * 輸出報表必須明確揭露「經由 API 取得的 0050 與 00631L 最新市場股價」。
  * 所有台幣金額（成本、市值、曝險、損益）必須自動加上千分位逗號（例如：`$1,250,000 元`）。
* **FR-03-3 百分比格式化：** 市值權重與投資報酬率（ROI）必須顯示至小數點後兩位，並加上 `%` 符號。

## 4. 非功能需求 (Non-Functional Requirements)

### 4.1 效能與網路響應時間 (Performance)
* 系統從發起外部股票 API 網路請求到完成整體槓桿計算，其總響應時間（Response Time）在正常網路環境下應 **< 2 秒**。
* 核心計算模組（Model）必須為純函數（Pure Function），確保其在無網路依賴下的單元測試執行時間 **< 10 毫秒**。

### 4.2 相容性與執行環境 (Compatibility)
* 程式必須能在 **Node.js v18、v20 及以上**（建議 LTS）環境中穩定執行。
* 後端以 **TypeScript** 撰寫，建置後於 Node.js 執行；開發階段使用 `tsx` 或同等工具。
* 網路請求所引用的第三方相依套件（如 `axios`、`express`）必須保持在穩定、無安全漏洞（Vulnerability）的版本。

### 4.3 程式碼健全性與維護性 (Maintainability)
* **邏輯解耦 (SoC)：** 負責「吃」外部 URL API 的程式碼（Service）、財務公式計算邏輯（Model）、與使用者輸入輸出介面（Interface）必須嚴格抽離，便於未來抽換 API 來源或改寫為機器人後端。
* **異常日誌記錄 (Error Logging)：** 當 API 觸發異常容錯防禦機制時，必須印出清楚的日誌描述，便於維護人員進行問題追蹤與排查。

## 5. 未來產品規劃藍圖 (Product Roadmap)

### 📌 階段一：核心引擎與 CLI 驗證（當前階段）
* 實作純 Node.js 環境下的核心計算模型。
* **串接 FinMind 開放 API，實現自動抓取最新股價功能**，完成終端機互動版本的工具。
* 確保財務計算公式與時間防禦、容錯機制 100% 正確。

### 📌 階段二：RESTful API 化與網頁端擴充
* 以 **Express.js + TypeScript** 將計算核心與自動抓取股價的邏輯封裝成 HTTP API（主要端點：`POST /api/v1/calculate-leverage`、`GET /api/v1/health`）。請求/回應格式與專案結構見 [技術開發文件](./technical-spec-express-typescript.md)。
* 開發一個極簡的網頁前端表單，讓使用者輸入庫存即可自動呼叫此後端 API。

### 📌 階段三：通訊軟體機器人對接 (LINE / WhatsApp Bot)
* 對接 **LINE Messaging API Webhook** 與 **WhatsApp Cloud API**。
* 當機器人收到用戶傳來的持股文字指令時，後端自動調用此 API 模組抓取即時市價，並回傳精美的圖文卡片（Flex Message）至使用者手機。
